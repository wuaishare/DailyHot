# 榜单变体感知元数据设计

**状态：** 已确认  
**日期：** 2026-09-15  
**范围：** DailyHot 排行条目的元数据解析与展示

## 背景与问题

DailyHot 已能从统一 Trends 接口获得小红书 PGY 多维榜单。阅读、点赞和收藏榜的条目都包含 `metrics.views`、`metrics.likes`、`metrics.comments`、`metrics.collects`，接口还返回 canonical `variant`。然而新的榜单流组件仍将 `item.hot` 固定渲染为“热度”，导致点赞榜等页面把当前排序指标错误标为热度；其他指标也没有进入该页面的信息层级。

该问题不是数据缺失，而是前端不同入口各自解析元数据，且部分入口没有感知榜单变体。

## 目标

1. 根据实际榜单变体确定主指标：阅读榜突出阅读，点赞榜突出点赞，收藏榜突出收藏，实时榜保留热度。
2. 主指标之外继续展示接口提供的其他有效指标，不伪造、不补零、不把无效值显示为可用数据。
3. 榜单流、首页悬浮详情、旧详情页和紧凑横向卡片共享同一套指标语义。
4. 使用主题色、字重和轻量轮廓共同表达主指标，不只依赖颜色。
5. 保持公开仓库的 provider-neutral 边界：能力由 canonical variant 和公共数据字段驱动，不写死小红书私有实现。

## 非目标

- 不更改后端排序算法或 PGY 授权流程。
- 不新增私有凭据、专有服务依赖或仅第一方部署可用的接口。
- 不改变 DailyHot `1.4.9` 产品 Release；仍由 Build Number 标识部署。
- 不在紧凑卡片中强行塞入全部指标，避免破坏可扫读性。

## 方案选择

### 方案 A：统一的变体感知元数据解析器（采用）

扩展现有 `rankingItemMeta`，由它解析 canonical variant、标记主指标、执行指标回退和本地化。所有展示入口消费同一结果。

优点是语义集中、测试边界清晰、后续其他来源也可复用；缺点是需要同步修改多个消费组件。

### 方案 B：在榜单流中局部替换“热度”标签

仅在 `CategoryStream` 根据路由显示阅读、点赞或收藏。

改动小，但仍保留多入口不一致，也不能稳定展示辅助指标，因此不采用。

### 方案 C：后端下发 `primaryMetric`

让 Trends 接口直接声明主指标。

权威性高，但当前 canonical variant 已足以确定语义，新增跨仓库契约的成本大于收益。若未来出现无法由 canonical variant 推导的复杂榜单，再演进到该方案。

## 架构与数据流

```text
Trends feed.variant + item.hot + item.metrics
                    │
                    ▼
          normalizeTrendsRankingResult
          保留实际 variant 到结果对象
                    │
                    ▼
     getRankingItemMeta(item, locale, context)
     ├─ 选择实际 variant，路由/控件值仅作回退
     ├─ 解析 primaryMetricKey
     ├─ 校验并格式化 metrics
     └─ 标记 isPrimary / primaryMetric
                    │
       ┌────────────┼────────────┬────────────┐
       ▼            ▼            ▼            ▼
 CategoryStream   HotList      List.vue  CategorySourceRail
 完整行内元数据   完整悬浮详情  完整详情   紧凑主指标
```

## 数据契约

### 变体到主指标的映射

| canonical variant | 主指标键 | 标签 |
| --- | --- | --- |
| `read-*` | `views` | 阅读 |
| `like-*` | `likes` | 点赞 |
| `collect-*` | `collects` | 收藏 |
| `hot` 或无法识别 | `hot` | 热度 |

`comments` 当前是辅助指标，不存在对应小红书主榜变体。

### 权威来源与回退

1. 优先使用接口结果中的 `variant`，避免路由状态与实际返回数据短暂不一致时误标。
2. 若接口没有 `variant`，使用当前组件的 active subtype。
3. 对阅读、点赞、收藏榜，主指标优先使用对应 `item.metrics` 值。
4. 主指标缺失但 `item.hot` 有效时，将 `hot` 作为该主指标的数值回退，并仍使用正确的阅读、点赞或收藏标签。
5. 若两者均缺失，则不显示主指标，不用 `0` 或其他指标伪装。
6. 只有有限且非负的数值才进入指标列表；真实的 `0` 必须保留。

### 解析结果

每个已解析指标至少包含：

- `key`：`views`、`likes`、`comments`、`collects` 或 `hot`；
- `label`：当前语言的可见标签；
- `numeric`：经过校验的原始数值；
- `value`：紧凑格式化后的值；
- `isPrimary`：是否为当前榜单主指标。

元数据结果同时暴露 `primaryMetric`，便于紧凑组件只取主指标；完整入口使用 `metrics` 数组。指标顺序为主指标优先，其余按阅读、点赞、评论、收藏排列，且不重复。

## 展示设计

### 榜单流 `CategoryStream`

- 在开启“摘要”时显示元数据行。
- 主指标排在第一位，使用主题色、较高字重、主题色淡背景和边框。
- 其他可用指标以弱色紧凑文本显示，使用间距或分隔而不是连续长句。
- 作者和发布时间作为上下文信息，视觉优先级低于全部数值指标。
- 窄屏允许自然换行，不横向滚动、不截断关键主指标。

### 首页卡片 `HotList`

- 列表本身继续保持紧凑。
- 悬浮/键盘聚焦详情显示作者、发布时间和全部有效指标。
- 当前榜单主指标采用同一主题强调样式。

### 旧详情页 `List.vue`

- 完整指标胶囊沿用现有布局。
- 当前主指标添加统一的 `is-primary` 语义类和强调样式。

### 横向卡片 `CategorySourceRail`

- 卡片空间有限，只显示当前主指标与作者。
- 不再将阅读、点赞或收藏值写成“热度”。
- 完整指标仍可在榜单流或详情入口查看。

## 本地化与可访问性

- 继续支持简体中文、繁体中文、英文、日文和韩文指标标签。
- 主指标不只靠主题色区分，同时使用字重、边框和轻背景。
- 文本顺序在 DOM 中与视觉顺序一致，屏幕阅读器会先读主指标。
- 深色与浅色主题均使用已有主题变量，避免硬编码仅适用于某一模式的颜色。
- 动效不参与信息表达，无需新增动画。

## 异常与降级

- 缺少 `metrics`：按当前变体将有效 `hot` 显示为正确的主指标。
- 缺少 `variant`：回退到当前控件或路由的 subtype。
- 未知变体：保持现有热度语义，避免错误猜测。
- 部分辅助指标缺失：只显示存在的指标，不保留空占位。
- 非法、负数、NaN 或无限值：丢弃。

## 测试与验收

### 自动化契约

1. `rankingItemMeta` 覆盖四类主指标映射、主指标优先排序、`hot` 回退、零值保留、无效值过滤和五种语言。
2. Trends 归一化契约确认 `feed.variant` 被保留。
3. 组件审计确认四个消费入口传入变体上下文，并渲染 `is-primary` 语义类。
4. 全量 `npm run build` 通过现有预构建审计、Vite 构建与 SEO 检查。

### 生产浏览器验收

- `hot`：显示热度，不伪装为阅读、点赞或收藏。
- `read-30d`：阅读为第一主指标，其他可用指标仍可见。
- `like-14d`：点赞为第一主指标，不再显示为热度。
- `collect-30d`：收藏为第一主指标。
- 主指标在浅色和深色主题中都有主题色、字重和轮廓强调。
- 移动视口不横向溢出，主指标不被截断。
- 小红书前 15 个封面继续通过同源图片代理成功加载。
- 控制台无新增 error 或 warning。

## 发布与回滚

- 使用一个短期产品分支、一个 PR 完成实现，合并后执行 Return-to-Trunk。
- 等待 merged `main` 的 Vercel 生产部署成功后再做浏览器验收。
- 回滚可以完整撤销该 PR；接口字段和现有 `item.hot` 保持向后兼容，因此无需数据迁移。
